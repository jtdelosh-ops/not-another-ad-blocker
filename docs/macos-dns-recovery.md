# macOS DNS recovery gates

The read-only preflight can now observe the current network location's persistent ID and the service IDs within that location. Apple's [System Configuration API](https://developer.apple.com/documentation/systemconfiguration/scnetworkconfiguration) provides these IDs independently of user-editable service names. The preflight cross-checks a primary IPv4 route against the native service's BSD device before reporting its ID. It never writes DNS settings, creates a recovery record, or declares a trial safe.

## Identity and context

The future recovery target needs the current location/set ID, service ID, and a verified identity for the **network attached to that service at activation time**. The set and service IDs remain useful when a service is renamed, but neither proves that the Mac is still on the same Wi-Fi network. A route interface or gateway alone is also insufficient: both can be reused after a network change. If the network context cannot be established or later differs, recovery must retain its record and report that manual attention is needed rather than overwrite a possibly new network's DNS settings.

Before activating on a service, the helper must capture its complete DNS configuration. `networksetup -getdnsservers` distinguishes an explicit server list from no explicit servers, but it does not describe all search domains, supplemental resolvers, managed DNS settings, or Network Extension policy. The helper must inspect the service's DNS protocol configuration and reject any mode it cannot round-trip exactly. Effective `scutil --dns` output remains an additional policy check, not the saved setting to restore.

## Offline helper and journal

The existing [platform-neutral controller](system-dns-design.md) already saves an original/applied setting before mutation, compares before writes, and retains a record on conflict. A Mac adapter must satisfy the same contract. It needs a separately launched, narrowly privileged settings/recovery helper in a protected local directory; the ordinary companion should not run as root. The helper must be installable and runnable independently of the resolver and browser, including after reboot or helper failure. Its recovery command must work offline without upstream DNS.

The helper's restore path must verify the saved location ID, service ID, network-context evidence, and current DNS setting. If the setting is already original, it can mark that target restored. If it is still exactly NAAB's applied setting in the same verified context, it can restore the complete original configuration and read it back. Any third-party edit, missing service, context change, unreadable record, or uncertain write must preserve the record and report a conflict. A schedule or `launchd` job may retry safe cases but must never force-reset DNS after a conflict.

The implementation includes a native comparison primitive for DNS protocol dictionaries. It parses both property lists and compares their values, so XML key order does not decide whether a setting changed. It rejects invalid or non-dictionary data. Apple's higher-level DNS getter can hide a real empty (or disabled-only) dictionary as null without resetting `SCError`; an earlier user observation of status 1004 therefore did not prove that the stored entity was absent. Capture and the locked restore comparison now read the raw DNS entity from the same preferences session, preserving even an empty dictionary. A missing/non-dictionary raw entity remains an error. Legacy records that lack an exact original dictionary are retained for manual attention rather than filled in by inference. No user-facing activation command creates a recovery journal yet.

This distinction follows Apple's [configuration getter and setter implementation](https://github.com/apple-oss-distributions/configd/blob/main/SystemConfiguration.fproj/SCNetworkConfigurationInternal.c). Native regression tests stage empty and disabled-only dictionaries in a separate, uncommitted temporary preferences session; they do not change system network settings.

The source now contains a guarded offline recovery command, a root-owned record store, and an optional `launchd` installation script. The command compares the saved location and service IDs, BSD device, primary IPv4 gateway address and gateway link-layer address, and complete DNS protocol dictionary. It restores only when the current dictionary still equals the recorded NAAB-applied dictionary. It verifies the original setting after writing and retains the record on conflict, missing context, or an uncertain result. The gateway identity is a conservative local-network check: a missing ARP entry or a changed router prevents automatic recovery, even when the service ID is unchanged. It is not a proof against a malicious network impersonating the original gateway.

`recovery.json` is private to root under `/Library/Application Support/NAAB-DNS-Preview`. The helper refuses a non-root caller, untrusted parent directories, unsafe ownership or modes, extended ACL entries on protected paths, and concurrent recovery. The installer also rejects inherited ACL entries on newly created files. An activation must write and sync this record before changing DNS; only the opt-in CI fixture described below currently creates one on Mac. The root-only recovery command is `sudo naab-dns-macos recover`. It does not need the resolver, browser, upstream DNS, or a live Internet connection.

On an **isolated test Mac**, after a successful native build and code review, the independent helper can be installed with:

```sh
cargo build --release --locked --manifest-path companion/Cargo.toml --bin naab-dns-macos
sudo sh scripts/install-macos-dns-recovery.sh companion/target/release/naab-dns-macos
```

The installer refuses to replace an existing helper while a recovery record is present. It installs a root-owned copy and a `launchd` task that runs at startup and every minute. Installation and the no-record recovery path passed on a disposable Intel Mac runner in [run 37067964310](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37067964310), commit `3985881`. The user's everyday Mac has exercised only the no-record recovery path; the persistent helper is not installed there. Do not treat a successful source build or read-only preflight as permission to start a system-DNS trial.

## Disposable runner restoration test

The `Mac preview` workflow has a manually selected `live_recovery` input (off by default). It builds the source-only `macos_recovery_ci` example and runs it as root on the workflow's disposable `macos-15-intel` VM, after installing the reviewed recovery helper. Do not run this fixture on an everyday Mac. Its environment acknowledgements prevent accidental invocation; they do not prove that a machine is isolated.

The fixture captures the current service's complete DNS dictionary, enabled state, and network context, then syncs the production recovery journal before making a native settings change. It keeps the runner's existing upstream addresses and adds a temporary `naab-ci.invalid` search-domain marker. It checks two cases:

1. The separate installed helper restores the complete original state after normal completion and clears the journal.
2. The fixture holder is killed with SIGKILL while its journal lock is held. The installed 60-second `launchd` schedule must restore the complete original state and clear the journal within 100 seconds, without a manual recovery call or task kickstart during the measured interval.

Both cases require native read-back and a successful `restored` report. Failure cleanup invokes the same conflict-safe helper and cannot turn a failed test into a pass. The workflow also checks for a retained journal as root, since an ordinary user cannot see inside the protected recovery directory. This test does not exercise loopback DNS forwarding, a public activation command, Ctrl+C handling, reboot, sleep/wake, Wi-Fi or VPN transitions, or all static/mixed settings. Those remain separate gates.

Both cases passed on the disposable Intel Mac in [run 37072269644](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37072269644), source commit `eae2bc4cb6e48f753f6b59afc16dd4656bc41c81`. The runner captured a present, enabled DNS protocol and its complete stored dictionary. The normal restoration and natural scheduled recovery after SIGKILL each restored the exact original dictionary and protocol state and cleared the journal. Final cleanup confirmed no pending recovery record. Native companion unit tests also passed (102 passed, 1 ignored), including the empty/disabled-only dictionary regressions; all workflow steps succeeded.

## Disposable runner loopback trial

The separate manual `live_loopback` workflow input (off by default) exercises the source-only fixture's `--loopback` mode. The driver requires both disposable-runner acknowledgements and the installed recovery task. The resolver starts in a separate process: a single-threaded bootstrap opens only IPv4/IPv6 loopback UDP/TCP port 53, clears supplementary groups, and drops to the non-root runner UID/GID before creating its runtime or processing packets. The ordinary server and Windows preview use the same listener/serving implementation. No privileged resolver service is installed.

Before changing DNS, the fixture captures the original full dictionary and upstream IPs, confirms the resolver's fresh health token directly on all four sockets, and verifies successful forwarded A answers over IPv4/IPv6 UDP/TCP with its cache disabled. It saves and syncs the journal before applying `127.0.0.1` and `::1`. In both live cases, a unique public test name must produce an expected negative answer through macOS's native `DNSServiceQueryRecord` API and a matching forwarded event in NAAB; both observations are required to establish uncached system passthrough. The callback distinguishes the native no-such-record code from timeout or daemon failure and rejects positive answers. Regression tests cover these distinctions without making DNS queries or changing settings.

The `.naab-health.invalid` token namespace is used only for direct loopback probes. System resolver APIs should synthesize negative responses for `.invalid` without querying DNS ([RFC 6761 section 6.4](https://www.rfc-editor.org/rfc/rfc6761#section-6.4)); an OS query for that name therefore cannot establish handoff to NAAB. Run `37080355106` returned native no-such-record for that test after direct listener probes had passed. Recovery restored the exact original state and cleared the record. The corrected OS test uses a fresh `naab-ci-<random>.example.com` name plus the resolver's forwarded event.

Run `37081060213` received the native negative answer but no matching forwarding event, so it failed and restored the original state. The fixture now logs effective resolver selection and polls with an eight-second readiness budget for a nonempty default DNS list using only NAAB loopback addresses, with no other unicast resolver addresses, stable for at least 500 milliseconds. Health, stored-setting, and context checks continue during this wait. The polling budget is checked between observations; utilities now use the bounded command runner described below, while native framework calls can still overrun a polling deadline. The workflow timeout and independent scheduled helper remain the fallback for this disposable fixture. This read-only readiness check precedes the system query; the matching forwarded event remains mandatory. A matching query reaching NAAB also logs its type and outcome for diagnosis.

The workflow explicitly selects Cloudflare's `1.1.1.1:53` and `1.0.0.1:53` through `NAAB_LOOPBACK_UPSTREAMS` for these disposable tests. Both must first return valid A answers over UDP and TCP. Captured runner upstreams are probed separately for diagnostics; the saved original DNS dictionary and network-context record are unchanged. Run `37080355106` confirmed that the runner gateway `192.168.64.1:53` answered UDP while its direct TCP probe timed out; both selected upstreams and NAAB's four listeners passed their forwarding probes. Production transport selection is unchanged: TCP clients use upstream TCP, as recommended by [RFC 5625 section 4.4.1](https://www.rfc-editor.org/rfc/rfc5625#section-4.4.1). Passing this fixture does not establish compatibility with every network's default DNS gateway.

The normal case monitors local health until its 15-second deadline, with a 30-second active-phase limit for system-query checks, then verifies exact restoration and journal removal before stopping the resolver. A second case kills only the resolver and requires three consecutive failed local health samples to trigger restoration. The independent scheduled helper remains installed as a fallback if the driver exits. This fixture watchdog is not a public Mac trial controller. Ctrl+C, reboot, sleep/wake, Wi-Fi/VPN transitions, broader static settings, and interrupted writes remain separate live gates; a signed installer and uninstall/upgrade verification also remain future work.

Both loopback cases passed on the disposable Intel Mac in [run 37081840007](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37081840007), source commit `f140d0a2cc599cde5128c5d12375d97df3588bd2`. In each case, effective default and scoped DNS used `127.0.0.1` and `::1`, and a fresh native system query produced the expected negative answer plus a matching forwarded A event from the unprivileged resolver. The normal deadline and the three-failure watchdog after resolver SIGKILL each restored the exact original DNS dictionary and protocol state, with `outcome: restored`, `recoveryPending: false`, and no remaining journal. Final cleanup and all workflow steps passed, including native companion tests (102 passed, 1 ignored) and two fixture callback tests.

This result covers one hosted macOS 15 Intel environment and the two explicit CI upstreams. The first recorded effective-DNS snapshot already contained both loopback addresses; this run does not establish the exact cause of the earlier missing forwarding event. It does verify handoff after the readiness check. The previous recovery-only cases retain their separate evidence above and were not repeated in this loopback-only run. These settings-changing fixtures must not be run on an everyday Mac.

## Foreground controller and cancellation gate

The library's `macos_trial` controller now owns journal-before-write activation, exact stored-state/context monitoring, a polling deadline capped at 300 seconds, three consecutive local-health failures, and restoration through the existing offline recovery implementation. It refuses a pending session and requires distinct, complete enabled DNS snapshots. Errors and unwinding panics during the active phase also attempt recovery; conflicts retain the journal. Native calls and caller callbacks can overrun the polling deadline, so this is not a hard process execution timeout. Bounded utility capture and conservative internal admission are described below; production lifecycle integration and a public trial interface remain unfinished.

The dedicated Mac helper can register SIGINT and SIGTERM streams synchronously before entering the controller. Tokio's process-lifetime signal handlers stay installed during restoration, including repeated signals. Signal handling only requests cleanup; settings changes run on the foreground thread. This guard is intended for a dedicated helper process, not an embedded application that expects its original signal disposition to be restored.

The manual `live_controller` workflow input is off by default and uses only the disposable hosted Mac. Four cases run the library controller with the same separate unprivileged loopback resolver and independent recovery fallback used above. The driver sends an actual SIGINT or SIGTERM after verified activation and repeats the signal during the cleanup path. Two deadline cases start from explicit static DNS: one IPv4 server, then an ordered list containing two IPv4 servers. Both also contain an ordered search-domain list. After establishing each static baseline, the fixture polls shared admission for up to ten seconds, requiring successful observations at least 500 milliseconds apart and checking the exact saved state/context on every iteration. Native calls can overrun that polling budget. A fifth case exercises offline recovery of a complete mixed dictionary containing two IPv4 servers, one IPv6 server, and ordered search domains; it does not activate the loopback controller. Every case requires exact native dictionary comparison, journal removal, and restoration of the initial runner baseline.

Static fixture setup intentionally establishes a temporary runner baseline before the controller saves its own record; this is not a supported nested production transaction. Abrupt fixture termination can leave that static baseline on the disposable VM. The fixture must never run on an everyday Mac. Controller cases verify native settings and direct resolver health; the separate `live_loopback` cases establish fresh system-query forwarding. Local transaction regressions cover pre-cancellation, pending sessions, journal failure, partial activation failure, notification errors/panics, DNS conflicts, resolver loss, failed restoration, and failed report writing. Native signal/static outcomes must be taken from the corresponding workflow result, not inferred from those local tests.

All four controller cases passed on the disposable Intel Mac in [run 37145598749](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37145598749), source commit `fcbdc5edd9d7733cba88f82d2f4e6c7dfe5b706a`. Actual SIGINT and SIGTERM each requested restoration, and a repeated signal during the cleanup path did not terminate the helper. Both static deadline cases restored the complete original dictionary, including ordered addresses and search domains, then returned the runner to its initial baseline. Every case required a successful restored report and a cleared journal. The same run repeated and passed both loopback cases, including fresh native system-query forwarding and restoration after resolver failure. Final cleanup reported no pending recovery record. Native companion unit tests (102 passed, 1 ignored), all seven controller transaction regressions, and both fixture callback tests passed; all workflow steps succeeded. The older recovery-only SIGKILL/scheduled case was not repeated in this run and retains its separate evidence above.

## Bounded utilities and internal admission

Mac service inventory, resolver preflight, and recovery gateway inspection now share a command runner with a five-second per-command deadline, bounded stdout, a 16 KiB stderr limit, closed stdin, and a fixed C locale/environment. Standalone inventory has a shared 15-second budget, full preflight 20 seconds, and each route/ARP context observation five seconds. Nonblocking pipes prevent noisy output or inherited pipe handles from holding up the deadline. Failures kill and reap the owned child; commands are fixed absolute-path utilities and never run through a shell. Process spawning, kernel kill/reaping, and native System Configuration framework calls are not hard real-time operations. The new limits therefore bound ordinary utility execution/capture, not every native call or the entire trial's wall-clock duration.

The controller's native adapter now rechecks admission before creating a journal. Cancellation and local resolver health are checked again after admission and immediately before the DNS write. The shared policy requires one unambiguous enabled service on an `en`-numbered primary interface (the device name does not prove its hardware type), a complete enabled DNS dictionary, consistent configured/effective server order, one ordinary default resolver with at most its matching primary scoped copy, and only standard mDNS entries. Unknown/supplemental/service-specific policies, competing services, unsupported addresses, duplicate/malformed fields, and unknown DNS dictionary keys are rejected. Supported original dictionaries are empty or contain only validated `ServerAddresses` and `SearchDomains`; exact original bytes are checked against the fresh native snapshot. Applied DNS must equal the fixed loopback dictionary. The admission schema uses Apple's [dictionary inspection API](https://developer.apple.com/documentation/corefoundation/cfdictionarygetkeysandvalues(_:_:_:)) and is separate from recovery, which continues preserving complete saved dictionaries without imposing new activation rules.

Admission is conservative snapshot validation, not an atomic view of all network subsystems or proof that managed DNS/VPN policy is absent. It does not authorize a public trial. The disposable fixture uses the shared gate, and the native controller repeats it after resolver startup. Local tests cover policy rejection and zero mutation on failed admission.

The first full admission run [37149517360](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37149517360), source `56246b3a30c8aae464812d3872f217886a7c3c74`, passed native tests and seven live cases but rejected the mixed static controller baseline before activation. Diagnostic run [37150306484](https://github.com/jtdelosh-ops/not-another-ad-blocker/actions/runs/37150306484), source `5a6049d4f4f6dbc6532df92953768ae4b50a7455`, repeatedly observed configured `[1.1.1.1, 1.0.0.1, 2606:4700:4700::1111]` and effective `[1.1.1.1, 1.0.0.1]` throughout the ten-second wait. Both failed runs restored the runner baseline and cleared the journal. The strict mismatch rejection is retained. Current fixtures use ordered IPv4 for admitted activation and separately verify that offline recovery preserves the complete mixed dictionary. This does not establish admitted mixed-family activation on this runner; the older mixed controller result above predates this admission gate. The revised nine-case live run is pending.

These results cover one hosted macOS 15 Intel environment. Bounded utility capture and conservative internal admission are implemented, awaiting native regression evidence. Public helper integration and broader admission/lifecycle validation remain future work. No user-facing activation command creates the journal or changes Mac DNS, and `trialReady` remains false. The test example is not included in the preview archive. Reboot/resume, sleep/wake, Wi-Fi/VPN transitions, interrupted writes, and installer upgrade/uninstall remain separate gates; standard hosted CI does not itself prove physical-device or reboot behavior.
